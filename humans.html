    Thruxion - Humans API

    API URL: https://thruxion.com/api/humans/

    The Humans API keeps a registry of people (humans) and what is known about them: their user accounts on different platforms, their skills and specialities, certificates, facial recognition records, bank cards and space-time records (where they were, and when). A human is the central record and everything else belongs to one.

    The documentation has code examples in Shell, Ruby, Python and JavaScript. The JavaScript examples run on Node.js with the axios package, plus form-data for file uploads.

    Conventions used by every endpoint:

    • Requests and responses are JSON. File uploads use multipart/form-data.
    • Every endpoint except System Login and Health Check needs a token in the Authorization header, as Bearer <token>.
    • IDs are integers.
    • Send dates as YYYY-MM-DD and date-times as YYYY-MM-DD HH:MM:SS. Responses return them in ISO 8601 format (UTC), for example 2026-01-13T00:40:56.000Z.

    Authentication

    The API uses JSON Web Tokens (JWT). Log in with a system account to get a token, then include it in the Authorization header of every other request:

    Authorization: Bearer <token>

    There are two system accounts, admin and dev, and their credentials are provided by Thruxion. They are different from the users stored by the API, who are the end users of your platforms.

    Every endpoint currently requires a token from the admin account. Tokens from the dev account are refused with 403.

    A request with a missing or rejected token gets one of these errors:

    Status Body Reason
    401 {"error": "Access denied"} No Authorization header.
    401 {"error": "Invalid Authorization format"} The header is not Bearer <token>.
    403 {"error": "Invalid token"} The token is invalid, expired or from the wrong account.

    Humans

    A human is the central record of the API. Users, certificates, facial recognition records, cards, space-time records and skill links all belong to a human.

    The Humans API uses the following status codes:

    Status Code Meaning
    400 Bad Request -- A parameter is missing or invalid, or the body is not valid JSON.
    401 Unauthorized -- The Authorization header is missing or malformed, or the credentials are wrong.
    403 Forbidden -- The token is invalid, expired or belongs to the wrong account, or the user account is inactive.
    404 Not Found -- The requested record does not exist.
    409 Conflict -- The email is already registered on that platform.
    429 Too Many Requests -- Too many login attempts. Wait 15 minutes and try again.
    500 Internal Server Error -- The request could not be completed. This includes duplicate values in unique fields, such as a human's unique_id.

    Validation errors (400) list every invalid field: path is the field name and location says where it was sent (body, params or query).

    Other errors carry a short text in error or message, for example {"error": "Invalid token"} or {"message": "Not found"}. The /human endpoints also include "success": false.

    Upload errors (a file type that is not allowed, or a file over the size limit) and bodies that are not valid JSON currently return an HTML error page instead of JSON.
